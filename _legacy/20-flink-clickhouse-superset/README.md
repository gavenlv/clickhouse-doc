**为什么是这套组合？**

| 组件 | 解决什么问题 | 替代方案 | 选择理由 |
|------|------------|---------|---------|
| **Flink** | 流式计算、状态管理、Exactly-Once | Spark Streaming、Storm | 真正的流式引擎（不是微批），事件时间 + 水位线成熟，状态后端可水平扩展 |
| **ClickHouse** | 亚秒级多维聚合、列存压缩 | Doris、StarRocks、ES | 写入吞吐高（百万行/秒），压缩比 10x+，SQL 兼容好，物化视图 / 投影丰富 |
| **Superset** | 拖拽式 BI、嵌入式分析 | Tableau、Grafana | 开源、可深度定制、原生支持 ClickHouse（HTTP/原生协议）、社区活跃 |

## 🎓 核心原则（贯穿全章）

1. **流批一体，存储分层** — Flink 做实时计算，ClickHouse 做存储，Superset 做展示，职责清晰
2. **写入用宽表，查询用预聚合** — 写入侧扁平化避免 JOIN，查询侧用物化视图 / 聚合表兜底
3. **按时间分区，按主键排序** — ClickHouse 的核心命脉，所有表都遵守
4. **指标下沉到数据层** — Superset 只做可视化，不做复杂计算（否则 BI 慢且不专业）
5. **每个决策都有 Why** — 写代码之前先回答"为什么这样设计"

## ⚠️ 适用边界

本章节方案**不适合**以下场景：
- 强事务型业务（如金融核心交易）→ 用 MySQL / OceanBase
- 离线批处理为主（>1h 延迟可接受）→ 用 Hive / Spark + Parquet
- 高频更新 / 单行随机写 → ClickHouse 的弱项，应改用 HBase / TiDB
