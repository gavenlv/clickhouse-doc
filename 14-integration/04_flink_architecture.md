## 1.3 关键设计决策（每个都有 Why）

### 决策 1：为什么用 Flink 而不是 Spark Streaming？

| 维度 | Flink | Spark Streaming |
|------|-------|-----------------|
| 计算模型 | 真正的流（每事件） | 微批（≥100ms 延迟） |
| 状态管理 | 内置 RocksDB，TB 级 | 需外部存储（Redis/HDFS） |
| Exactly-Once | 原生支持 | 需手动实现 |
| 事件时间 | 一等公民 | 弱（Structured Streaming 才改进） |
| 延迟 | 毫秒级 | 秒级 |

**Why**：实时分析要求**秒级延迟**，Flink 的流式模型 + 事件时间语义是唯一选择。

### 决策 2：为什么用 ClickHouse 而不是 Elasticsearch / Doris？

| 维度 | ClickHouse | Elasticsearch | Doris |
|------|-----------|---------------|-------|
| 写入吞吐 | 百万/秒 | 10万/秒 | 50万/秒 |
| 聚合查询 | ★★★★★ | ★★ | ★★★★ |
| 全文检索 | ★★ | ★★★★★ | ★★ |
| 压缩比 | 10x+ | 2-3x | 5x |
| 运维复杂度 | 中 | 高 | 中 |

**Why**：本场景是**结构化数据 + 聚合分析**，不是日志检索，ClickHouse 是最优解。**注意**：如果业务包含大量全文检索，应选 ES。

### 决策 3：为什么数据要分层（ODS/DWD/DWS/ADS）？

```
┌────────────────────────────────────────────────────────────────┐
│                  分层架构的本质：解耦 + 复用                       │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│  不分层的问题:                                                 │
│  ┌─────────┐   一张超级大表   ┌──────────┐                    │
│  │ 业务需求A│ ─────────────► │  表结构   │                    │
│  │ 业务需求B│   (改表频繁)   │  难维护   │                    │
│  │ 业务需求C│   (数据冗余)    │  难复用   │                    │
│  └─────────┘                 └──────────┘                    │
│                                                                │
│  分层后:                                                       │
│  ODS  原始数据,    不做清洗,    可回溯                                       │
│        ▼                                                              │
│  DWD  清洗+去重+标准化, 业务过程清晰                                        │
│        ▼                                                              │
│  DWS  轻度聚合(分钟/小时), 跨域复用                                          │
│        ▼                                                              │
│  ADS  高度聚合(应用主题), 直接服务看板                                        │
│                                                                │
│  收益:                                                          │
│  - 改一个业务需求, 只动 ADS, 不影响 DWS/DWD                              │

│  - ODS 保留原始数据, 出问题时可重算                                          │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

### 决策 4：为什么 Flink Sink 要做批量写入而不是逐条写？

```java
// ❌ 错误：逐条写入
for (OrderEvent event : stream) {
    jdbcSink.execute("INSERT INTO orders VALUES (...)", event);
}
// 问题：每次都是一次 RPC + 一次 part 创建，100万事件 = 100万次写入

// ✅ 正确：批量写入
stream.addSink(new ClickHouseSink(
    batchSize = 5000,        // 每 5000 条 flush
    flushInterval = 1000,    // 或每 1 秒 flush
    maxRetries = 3
));
```

**Why**：ClickHouse 的**写入性能与批次大小强相关**。
- 单条写入：~1000 行/秒（part 创建开销占主导）
- 批量 1000：~10万 行/秒
- 批量 10000：~100万 行/秒

**批量是 ClickHouse 性能的第一原则**。

## 1.4 容量规划参考

| 业务规模 | 日数据量 | Flink 并行度 | ClickHouse 节点 | Superset Worker |
|---------|---------|-------------|-----------------|-----------------|
| 中小 (DAU 10万) | 1000万行 | 4-8 | 3 节点 (2 副本) | 2 |
| 中型 (DAU 100万) | 1亿行 | 16-32 | 6 节点 (2 副本) | 4 |
| 大型 (DAU 1000万) | 10亿行 | 64-128 | 12+ 节点 (2 副本) | 8+ |

**容量规划公式**：
- Flink 并行度 ≈ Kafka 分区数（一一对应，避免数据倾斜）
- ClickHouse 节点数 = (日数据量 × 保留天数 × 副本数) / 单节点容量(2TB)
- Superset 内存 = (并发查询数 × 单查询内存 500MB) × 1.5

## 1.6 常见误区（先避坑）

| 误区 | 后果 | 正确做法 |
|------|------|---------|
| 把 Flink 当 ETL 工具用 | 状态失控，OOM 频繁 | Flink 只做流式增量逻辑，复杂 ETL 放 Spark |
| 全部数据进 DWD，DWS 直接算 | DWS 查询慢如蜗牛 | 高频聚合下沉到 DWS 物化 |
| Superset 里写复杂 JOIN | BI 报表 30s+ 出不来 | JOIN 提前到 ClickHouse 视图层 |
| ClickHouse 表用 UUID 主键 | 写入极慢 | 用业务字段 (user_id, event_time) 排序 |
| 不做监控就上线 | 半夜被叫起来排查 | 至少监控：写入速率、合并队列、查询 P99、磁盘 |
