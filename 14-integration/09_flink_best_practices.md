# 06 - 行业最佳实践与"为什么"

> **本章定位**：经验沉淀。每个结论都附带**为什么这么选**，让你**知其然更知其所以然**，能够根据自己业务灵活变通。

## 6.1 Flink 端最佳实践

### 实践 1: 始终启用 Checkpoint,绝不裸跑

```
❌ 反模式: 实时作业不开 Checkpoint
   "重启后会丢数据" 
   "上线初期没出问题"  → 第一次故障时数据全丢

✅ 最佳实践: 默认开启,合理配置
   间隔: 60 秒
   超时: 120 秒
   状态后端: RocksDB
   存储: HDFS/S3
```

**Why（为什么必须这样）？**

| 场景 | 不开 Checkpoint | 开 Checkpoint |
|------|----------------|---------------|
| 正常重启 | 数据从最新 offset 重读(丢中间状态) | 状态恢复,Exactly-Once |
| 节点故障 | Subtask 全挂,人工介入 | 自动重启,无感恢复 |
| 业务高峰 | 状态丢失,数据重复/缺失 | 状态保留,数据准确 |
| 运维成本 | 半夜被叫起来修数据 | 一觉到天亮 |

**核心思想**：**Checkpoint 是 Flink 的"保险",不开启等于裸奔。** 即便你的业务是"日志采集,丢一点没关系",Checkpoint 也能让你在故障时**几秒内恢复**,而不是几小时。

### 实践 2: 业务方期望的延迟 = 你设计的 SLA

```
真实案例:
  业务方: "我要实时大屏,GMV 实时刷新"
  开发: "好,5 秒延迟"  → 上线后业务方吐槽"太慢了"
  
  真实: 5 秒延迟 = 业务感知"卡顿"
       1 秒延迟 = 业务感知"还行"
       100 毫秒 = 业务感知"实时"
```

**Why？**
- 人对"实时"的感知阈值是 **200ms - 1s**
- 5 秒以上的延迟,用户会反复刷新页面(放大流量)
- **SLA 设计原则**：把"业务期望延迟"作为硬指标,反推架构设计

**SLA 分级**：

| 业务场景 | 期望延迟 | 架构要求 | 成本 |
|---------|---------|---------|------|
| 实时大屏 / 监控告警 | < 1s | 内存计算 + 物化视图 | 高 |
| 业务看板 | 1-5s | Flink 流式 + 物化视图 | 中 |
| 准实时分析 | 5-60s | Flink 微型批 + 视图 | 低 |
| 离线报表 | 1h+ | Spark + Parquet | 极低 |

**核心思想**：**SLA 决定架构,不是反过来**。如果业务说"5 分钟延迟可以",你就用微型批,省 80% 成本。

### 实践 3: 状态是"双刃剑",慎用大状态

```
真实案例:
  某作业: 用 ValueState 缓存了 5000 万用户画像
  问题: 作业重启需要 30 分钟恢复(RocksDB 加载)
  后果: 错过业务高峰

✅ 正确做法:
  - 状态 < 1 GB: 内存状态 + Checkpoint
  - 状态 1-10 GB: RocksDB + 增量 Checkpoint
  - 状态 10-100 GB: RocksDB + 本地恢复 + 异步快照
  - 状态 > 100 GB: 拆作业 / 改架构(用外部存储)
```

**Why？**
- Flink 状态管理强大,但"大状态"是隐形炸弹
- 每次 Checkpoint = 序列化 + 写 HDFS
- 大状态 = 长 Checkpoint + 慢恢复
- **经验值**: 单 TM 状态 < 10 GB 较安全

**核心思想**：**能用外部存储(Redis/HBase/ClickHouse)解决的,别放 Flink 状态**。Flink 状态适合"逻辑相关、生命周期对齐作业"的数据。

### 实践 4: 监控告警必须 3 选 1

```yaml
# 必监控 3 个核心指标(其他都是锦上添花)

# 1. Checkpoint 时长(稳定性)
checkpoint_duration:
  threshold: 5min    # > 5 分钟告警
  why: Checkpoint 超时 → 作业重启 → 数据延迟

# 2. 数据延迟(业务感知)
data_lag:
  threshold: 60s     # > 60 秒告警
  why: 延迟高 → 业务方投诉

# 3. 反压时长(健康度)
backpressure:
  threshold: 10%     # > 10% 时间反压告警
  why: 持续反压 → 数据堆积 → OOM
```

**Why？**
- 90% 的 Flink 故障都可以从这 3 个指标预测
- 监控告警 = 提前 5-30 分钟发现问题
- **不监控 = 等用户来报障**(通常延迟 1-2 小时)

**核心思想**：**监控不是为了排查,而是为了不被半夜叫起来**。

## 6.2 ClickHouse 端最佳实践

### 实践 1: 表设计先想 3 个问题

```sql
-- 在 CREATE TABLE 前,先问自己:
-- Q1: 这张表要支持哪些查询?
-- Q2: 查询的过滤条件是什么?
-- Q3: 数据保留多久?

-- 示例: 订单明细表
-- Q1: 用户行为分析、订单查询、漏斗分析
-- Q2: 时间范围 + 用户 ID + 地区
-- Q3: 1 年

-- 答案决定表设计:
PARTITION BY toYYYYMM(order_time)  -- Q3 决定
ORDER BY (order_time, user_id, order_id)  -- Q1+Q2 决定
TTL toDate(order_time) + INTERVAL 365 DAY  -- Q3 决定
```

**Why？**
- ClickHouse 表一旦建好,**修改 ORDER BY 代价极大**(需 INSERT 重新排序)
- 一次想清楚,胜过后期 10 次重构
- **核心原则**：**ORDER BY 是 ClickHouse 表的"灵魂"**,决定 90% 查询性能

### 实践 2: 永远不要"业务字段在主键最前"

```sql
-- ❌ 错误示例: 主键 = 业务主键
CREATE TABLE dwd_order (
    order_id  String,
    user_id   UInt64,
    order_time DateTime,
    amount    Decimal(18,2)
) ENGINE = MergeTree()
ORDER BY (order_id);  -- 业务主键在前

-- 问题:
-- 1. 查"最近 7 天的订单" → 全表扫描(无法走分区裁剪,因为分区键是 order_time)
-- 2. 查"用户 A 的订单" → 散落在多个 part,索引失效
```

**Why？**

- ClickHouse 主键是**稀疏索引**(每 8192 行一个标记)
- 主键顺序 = 数据物理排序顺序
- **查询时,主键前缀匹配的列过滤效率最高**
- 时间字段在前的"原因"：**99% 查询带时间范围**,时间在前 → 走分区裁剪 + 主键索引,过滤 99% 数据

**反模式**：
- ❌ `ORDER BY (order_id)` — 业务主键在前
- ❌ `ORDER BY (user_id, order_time)` — 时间不在前
- ❌ `ORDER BY (status, order_time)` — 低基数字段在前(压缩比低)

**核心思想**：**时间字段必须在 ORDER BY 最前**。这是 ClickHouse 设计的"硬性要求"。

### 实践 3: 物化视图 = 性能核武器,但有代价

```
┌────────────────────────────────────────────────────────┐
│              物化视图的取舍                               │
├────────────────────────────────────────────────────────┤
│                                                        │
│  收益:                                                  │
│    ✓ 查询速度 10-100 倍                                │
│    ✓ 数据库压力 -80%                                   │
│    ✓ 写入延迟 < 1 秒(自动增量更新)                      │
│                                                        │
│  代价:                                                  │
│    ✗ 存储增加 10-30%                                    │
│    ✗ 写入增加 5-15% 开销                                │
│    ✗ 修改定义麻烦(需删除重建)                           │
│                                                        │
│  何时用:                                                │
│    ✓ 高频查询(>10 QPS)                                │
│    ✓ 聚合逻辑固定                                       │
│    ✓ 维度变化不大                                       │
│                                                        │
│  何时不用:                                              │
│    ✗ 一次性查询                                         │
│    ✗ 维度变化频繁                                       │
│    ✗ 存储紧张                                           │
│                                                        │
└────────────────────────────────────────────────────────┘
```

**Why？**
- 物化视图不是"免费的午餐",有真实成本
- 盲目建 50 个物化视图 = 写入性能下降 + 存储翻倍
- **经验值**：**物化视图数量 < 10 个,聚合维度数 < 5 个**

**核心思想**：**物化视图是"预计算"的艺术,用空间换时间**。**高频 + 固定维度**才值得。

### 实践 4: 用 Dictionary 替代 JOIN

```sql
-- ❌ 错误: 直接 JOIN
SELECT o.order_id, u.user_name, u.user_tier
FROM dwd_order o
LEFT JOIN dim_user u ON o.user_id = u.user_id;

-- 问题: ClickHouse JOIN 是 O(N*M),千万行变亿次计算

-- ✅ 正确: 用 Dictionary
CREATE DICTIONARY dict_user (
    user_id UInt64,
    user_name String,
    user_tier String
) PRIMARY KEY user_id
SOURCE(CLICKHOUSE(DB 'dim' TABLE 'user'))
LIFETIME(MIN 60 MAX 300)
LAYOUT(HASHED());

SELECT
    o.order_id,
    dictGet('dict_user', 'user_name', o.user_id) AS user_name,
    dictGet('dict_user', 'user_tier', o.user_id) AS user_tier
FROM dwd_order o;

-- 性能对比(千万订单 × 百万用户):
-- LEFT JOIN:        30 秒
-- dictGet:          2 秒  (15x 提升)
-- 内存占用:         < 1 GB (Dictionary)
```

**Why？**
- ClickHouse JOIN 会触发数据重分布(分布式场景)
- Dictionary 是**预加载到内存的哈希表**,O(1) 查询
- 不需要改 SQL 结构,直接函数调用

**核心思想**：**维表 < 1000 万行 + 高频 JOIN → Dictionary**。比 LEFT JOIN 快 10-20x。

### 实践 5: 物化视图 + Dictionary + AggregatingMergeTree = 性能三件套

```
┌────────────────────────────────────────────────────────┐
│            ClickHouse 性能三件套                         │
├────────────────────────────────────────────────────────┤
│                                                        │
│  1. 物化视图                                            │
│     - 自动预聚合                                         │
│     - 写入时增量更新                                     │
│     - 适用: 高频查询的固定聚合                           │
│                                                        │
│  2. Dictionary                                          │
│     - 维表内存缓存                                       │
│     - O(1) 查询                                         │
│     - 适用: 高频维表关联                                 │
│                                                        │
│  3. AggregatingMergeTree                                │
│     - 手动控制预聚合                                     │
│     - 支持 uniq / quantile 等复杂聚合                    │
│     - 适用: 物化视图满足不了的场景                       │
│                                                        │
│  三者组合 = 性能最强 ClickHouse                          │
│                                                        │
└────────────────────────────────────────────────────────┘
```

**Why？**
- 这三个是 ClickHouse 设计的精髓
- 组合使用可以解决 95% 的性能问题
- 单独使用每一个都有效,但组合威力更大

## 6.3 Superset 端最佳实践

### 实践 1: "指标字典"是 Superset 治理的核心

```
真实案例:
  - 业务 A: "GMV 应该是销售额"
  - 业务 B: "GMV 应该是订单总额"
  - 业务 C: "GMV 应该是支付总额"
  → 三个看板三个数,业务方混乱

✅ 正确做法: 
  - 在 ClickHouse 端定义标准视图(v_metrics_standard)
  - 在 Superset 中把指标列标记为 "Certified"
  - 文档化指标定义 (放在数据集的 Description)
  - 所有看板强制使用 "Certified" 指标
```

**Why？**
- 指标口径不一致是 BI 项目的头号杀手
- 一旦发生"两个看板数不一样",用户会**对所有看板失去信任**
- **Certified 指标 = 唯一可信源**

**核心思想**：**指标不是定义一次就够了,需要持续治理**。**配置指标字典 → 文档化 → 培训 → 监督**。

### 实践 2: 看板分级管理

```
┌────────────────────────────────────────────────────────┐
│              看板分级与性能策略                            │
├────────────────────────────────────────────────────────┤
│                                                        │
│  Tier 1: 战略级 (CEO/CFO 看板)                           │
│    - 数据: 物化视图(预聚合)                              │
│    - 缓存: 5 分钟                                       │
│    - 图表数: < 10                                        │
│    - 刷新: 1 分钟                                       │
│    - SLA: 100% 可用                                     │
│                                                        │
│  Tier 2: 战术级 (部门经理)                               │
│    - 数据: DWS 汇总表                                    │
│    - 缓存: 15 分钟                                      │
│    - 图表数: < 20                                        │
│    - 刷新: 手动                                          │
│    - SLA: 99% 可用                                      │
│                                                        │
│  Tier 3: 运营级 (业务运营)                               │
│    - 数据: DWD 明细表                                    │
│    - 缓存: 5 分钟                                       │
│    - 图表数: < 15                                        │
│    - 刷新: 5 分钟                                       │
│    - SLA: 95% 可用                                      │
│                                                        │
│  Tier 4: 探索级 (数据科学家)                             │
│    - 数据: 全部 DWD                                      │
│    - 缓存: 无(或 1 分钟)                                │
│    - 限制: SQL Lab 行数限制                              │
│    - SLA: 尽力而为                                      │
│                                                        │
└────────────────────────────────────────────────────────┘
```

**Why？**
- 不同看板的重要性、性能要求差异巨大
- 统一对待 = 资源浪费 / 关键看板性能不足
- **分级管理 = 资源精准分配**

**核心思想**：**资源是有限的,用在刀刃上**。CEO 看板性能 +50%,可能价值 1000 万;探索看板性能 +50%,可能价值 1 万。

### 实践 3: Superset 缓存不是"银弹"

```
真实案例:
  - 业务: "我配置了 Redis 缓存,为什么看板还是慢?"
  - 排查: Superset 查询时根本没命中缓存
  - 原因: 用户每次点击不同筛选条件,缓存键变化,命中率 0%

✅ 正确使用:
  - 时间筛选器固定默认值(如 "最近 7 天")
  - 减少不必要的筛选器
  - 关键看板强制缓存(后端配置)
```

**Why？**
- 缓存键 = 看板 + 图表 + 所有筛选条件
- 筛选条件多 = 缓存键组合爆炸 = 命中率低
- **缓存是减少重复查询,不解决"查询本身慢"**

**核心思想**：**先让查询快(物化视图),再让缓存命中(减少筛选)**。**顺序不能反**。

## 6.4 端到端最佳实践

### 实践 1: 数据流的"三不原则"

```
┌────────────────────────────────────────────────────────┐
│                    数据流三不原则                          │
├────────────────────────────────────────────────────────┤
│                                                        │
│  1. 不在 Flink 端做"复杂业务"                            │
│     - Flink 只做: 清洗、维表关联、轻度聚合               │
│     - 复杂业务逻辑放: 应用层/业务库                       │
│     - Why: Flink 状态宝贵,业务变更频繁,难维护            │
│                                                        │
│  2. 不在 ClickHouse 端做"无必要的 JOIN"                  │
│     - JOIN 提前在 Flink 端做完                           │
│     - 维表关联用 Dictionary                              │
│     - Why: ClickHouse JOIN 慢且占资源                    │
│                                                        │
│  3. 不在 Superset 端做"复杂计算"                         │
│     - Superset 只做: 简单 SUM/AVG + 维度筛选             │
│     - 复杂计算在 ClickHouse 端                           │
│     - Why: Superset 查询并发高,数据库压力大              │
│                                                        │
└────────────────────────────────────────────────────────┘
```

**Why？**
- 每个组件有自己的"擅长"和"不擅长"
- 让每个组件做擅长的事 = 整体最优
- **架构的本质 = 让对的人做对的事**

**核心思想**：**职责分离**。**每个组件只做"自己最擅长的事"**。

### 实践 2: "云原生 + 监控"才是现代架构

```
传统架构:
  ┌────────┐    ┌────────┐    ┌────────┐
  │ 物理机  │    │ 物理机  │    │ 物理机  │
  │  部署   │    │  部署   │    │  部署   │
  └────────┘    └────────┘    └────────┘
  扩容: 买机器(几天)    监控: 自己搭(复杂)

现代架构(Kubernetes):
  ┌──────────────────────────────┐
  │   K8s Cluster (容器化)        │
  │   ┌────┐ ┌────┐ ┌────┐     │
  │   │ Pod│ │ Pod│ │ Pod│     │
  │   └────┘ └────┘ └────┘     │
  └──────────────────────────────┘
  扩容: kubectl scale(秒级)    监控: Prometheus + Grafana(开箱即用)
```

**Why？**
- K8s 提供: 自动扩缩、滚动升级、自愈
- 云原生监控: Prometheus + Grafana + AlertManager,完整的可观测性
- 物理机时代: 一切靠"运维同学的人力"
- **核心思想**：**让机器做机器擅长的事(弹性、可观测),人做人擅长的事(业务设计)**

### 实践 3: 文档化是"被忽视的最佳实践"

```
真实案例:
  上线 3 个月,无人能解释为什么"订单状态"在 02 章是 Enum,04 章是 String
  上线 6 个月,新员工不知 ORDER BY 为啥这样设计
  上线 12 个月,作者离职,代码无人敢动

✅ 正确做法:
  - 设计文档: 为什么这么设计(Why > What)
  - 数据字典: 每个字段的含义、口径、来源
  - Runbook: 故障处理 SOP
  - ADR (Architecture Decision Record): 关键决策记录
```

**Why？**
- 90% 的代码 3 个月后没人记得为什么这么写
- 没有文档 = 项目变成"传男不传女"的秘术
- **文档不是负担,是"未来对自己的善意"**

**核心思想**：**写代码是 1 次,读代码是 100 次**。**为未来的读者(可能也是你自己)写好注释和文档**。

## 6.5 常见反模式(避坑指南)

| # | 反模式 | 后果 | 正确做法 |
|---|--------|------|---------|
| 1 | Flink 不开 Checkpoint | 故障丢数 | **必须开启** |
| 2 | ClickHouse 主键是 UUID | 写入慢 100x | 用业务字段 |
| 3 | 物化视图不加过滤 | 存储爆炸 | 必须带时间范围 |
| 4 | Superset 里写复杂 JOIN | 看板 30s+ | JOIN 提前到 ClickHouse |
| 5 | 数据类型全部 String | 压缩比低 5x | 用最小合适类型 |
| 6 | 业务系统直连 BI 数据库 | 数据库被压垮 | 用专用数据集 + 物化视图 |
| 7 | 不监控就上线 | 半夜救火 | 至少 3 个核心指标 |
| 8 | 一次性导入 1 亿条 | OOM | 批量 + 并行 |
| 9 | 用 mutation 删大量数据 | 表卡死 | 用分区删除 |
| 10 | 频繁改 ClickHouse 表结构 | 数据重写 | 设计阶段想清楚 |

```
│                                                          │
│  腾讯:                                                    │
│    - Flink + ClickHouse(腾讯云 ClickHouse)               │
│    - 模型: ODS/DWD/DWS/ADS + 实时数仓                     │
│    - 业务: 游戏、电商、广告                                  │

│  Uber:                                                    │
│    - Flink + Pinot(类似 ClickHouse)                       │

│    - 经验: Schema 提前设计,迭代成本高                       │

│  Netflix:                                                 │

│    - 重点: 实时用户行为分析                                 │
```

## 6.7 团队协作最佳实践

```
│                  团队协作三件套                             │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  1. Code Review                                          │
│     - 所有 Flink SQL / ClickHouse DDL 必须 review         │

│     - Why: 一次误操作 = 几小时故障                        │
│                                                          │
│  3. 故障复盘                                              │
│     - 每次 P0/P1 故障后写复盘文档                         │
│     - 重点: 根因 + 改进措施 + 验证方法                     │
│     - Why: 不复盘 = 重复踩坑                              │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## 6.8 终极心法(给架构师)

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│  1. 简单优于复杂                                          │
│     - 一个简单物化视图,胜过 100 行 SQL 调优                │
│     - 简单方案 = 易维护 = 易传承                           │
│                                                          │
│  2. 测量优于猜测                                          │
│     - 没有 profile,就没有优化                            │
│     - 95% 的"性能问题"是架构问题,不是参数问题               │
│                                                          │
│  3. 架构优于调参                                          │
│     - 改架构收益 = 改 100 个参数                           │
│     - 投入产出比 = 100x                                   │
│                                                          │
│  4. 演进优于一步到位                                      │
│     - v1: 先解决 80% 的问题                               │
│     - v2: 优化 20% 的边角案例                              │
│     - 完美是进化的敌人                                    │
│                                                          │
│  5. 业务理解是基础                                       │
│     - 不懂业务,任何技术都是空中楼阁                        │
│     - 数据模型的本质是"业务的抽象"                         │
│                                                          │
│  6. 持续学习                                              │
│     - ClickHouse 每年 4 个大版本,功能日新月异              │
│     - Flink 每年 2 个大版本,API 不断演进                   │
│     - 保持学习,才不会被淘汰                                │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## 6.9 决策清单(遇到问题时的检查表)

```
遇到性能问题,按顺序检查:
□ 1. 是否用了物化视图?(80% 性能问题靠这个)
□ 2. 数据集选型是否合理?(虚拟 vs 物化)
□ 3. ORDER BY 是否最优?
□ 4. 是否有数据倾斜?
□ 5. 缓存是否生效?
□ 6. SQL 是否走了主键索引?(EXPLAIN)
□ 7. 是否有慢查询?(system.query_log)
□ 8. 服务器资源是否打满?(CPU/内存/磁盘)
□ 9. 网络是否有瓶颈?
□ 10. Flink 是否有反压?
```

## 6.10 写在最后

**架构没有银弹,只有权衡**。
- 没有"最好"的架构,只有"最适合"业务的架构
- 所有决策都是 trade-off:性能 vs 成本 / 实时 vs 复杂度 / 一致性 vs 可用性
- **理解每个决策背后的 Why,比记住 How 更重要**

**技术是手段,业务是目的**。
- 任何不为业务创造价值的技术优化都是浪费
- 永远问"这个优化给业务带来什么价值?"

**持续演进,小步快跑**。
- 完美架构不存在,适合的才是最好的
- 持续迭代,持续优化,持续学习
