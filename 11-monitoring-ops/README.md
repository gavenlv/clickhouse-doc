# ClickHouse 运维监控合并教程

## 本章解决的核心痛点

ClickHouse 运维团队在日常工作中常面临以下 10+ 个痛点：

| # | 痛点 | 本章解决方案 |
|---|------|-------------|
| 1 | **集群健康状态不可见** — 节点宕机、副本滞后、Part 异常无法及时发现 | `01_system_monitoring.sql` — 一键健康检查 + 系统表体系 |
| 2 | **备份恢复流程混乱** — 全量/增量策略不清，恢复时间不可控，RTO/RPO 无法达标 | `02_backup_recovery.sql` — BACKUP/RESTORE 深度指南 + 灾难恢复演练 |
| 3 | **告警配置不合理** — 阈值设得太松漏报、太紧告警风暴，值班人员被频繁骚扰 | `03_alerting.sql` — 分级告警阈值推荐 + 告警降噪 + 升级机制 |
| 4 | **Prometheus 集成门槛高** — 不知道暴露哪些指标、如何配置 Grafana 面板 | `04_prometheus_grafana.sql` — 开箱即用的 Prometheus 指标采集 + Grafana 面板设计 |
| 5 | **容量规划靠估** — 磁盘写满才发现、内存 OOM 频发、CPU 长期过载 | `05_capacity_planning.sql` — 增长预测 + 磁盘/内存/CPU 规划公式 |
| 6 | **存储成本居高不下** — 热冷数据混存，SSD 浪费严重，缺乏分层策略 | `06_tiered_storage.sql` — TTL MOVE TO + 多卷存储 + S3 冷备 |
| 7 | **日常维护缺乏规范** — 合并积压无人管、Part 碎片膨胀、元数据泄露 | `07_routine_maintenance.sql` — 日/周/月维护清单 + 自动化脚本 |
| 8 | **副本延迟不可控** — 查询读到过期数据，业务方投诉数据不一致 | `01_system_monitoring.sql` — replica 延迟监控 + 复制队列异常检测 |
| 9 | **Mutation 卡住集群** — 大范围 UPDATE/DELETE 导致 Parts 无法合并，查询变慢 | `01_system_monitoring.sql` — mutation 进度监控 + 阻塞检测 |
| 10 | **灾难恢复没演练** — 真出问题时手忙脚乱，恢复时间远超预期 | `02_backup_recovery.sql` — 灾难恢复演练脚本 + 恢复时间评估 |
| 11 | **数据质量无保障** — 重复数据、分区倾斜、空值异常 | `01_system_monitoring.sql` — 数据倾斜检测 + 分区空洞扫描 |
| 12 | **跨团队协作困难** — 缺少统一的运维视图和报告 | 本章提供标准化 SQL 模板 + Grafana 仪表盘模板 |

## 核心原理

### 系统表体系

ClickHouse 的系统表是运维监控的核心数据源，理解它们之间的关系是高效运维的基础：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        系统表体系关系图                                        │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  实时状态类 (即时查询，无需保留)              历史日志类 (需配置保留周期)          │
│  ┌────────────────────────┐                ┌────────────────────────┐       │
│  │ system.metrics         │                │ system.query_thread_log│       │
│  │ system.events          │                │ system.query_log       │       │
│  │ system.asynchronous_   │                │ (已禁用, 用 thread_log)│       │
│  │   metrics              │                │ system.text_log        │       │
│  │ system.processes       │                │ system.metric_log      │       │
│  │ system.merges          │                │ system.asynchronous_   │       │
│  │ system.replicas        │                │   metrics_log          │       │
│  │ system.clusters        │                │ system.session_log     │       │
│  │ system.disks           │                │ system.trace_log       │       │
│  └────────────────────────┘                └────────────────────────┘       │
│           │                                         │                       │
│           ▼                                         ▼                       │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │                    数据持久化层 (system.parts)                        │   │
│  │  • 所有表的所有 Part 元数据 (active/inactive, level, rows, bytes)     │   │
│  │  • 所有副本的 Part 信息 (通过 replica_num 区分)                       │   │
│  │  • Part 生命周期监控的核心入口                                        │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

### ClickHouse Keeper 监控

ClickHouse Keeper（替代 ZooKeeper）是复制表和高可用性的基石：

- **会话健康**：`system.replicas.is_session_expired` — 会话过期意味着副本不可用
- **队列深度**：`system.replication_queue` — 待处理复制任务数量
- **延迟指标**：`system.replicas.absolute_delay` — 副本落后主副本的秒数
- **读写状态**：`system.replicas.is_readonly` — 只读副本无法服务写入

### Part 生命周期监控

ClickHouse 数据以不可变的 Part 为单位存储，其生命周期包括：

```
写入 → 临时 Part → 活跃 Part → 合并 Part → 非活跃 Part → 清理
                                                      ↓
                                              分离 Part (detached)
```

- **活跃 Part 数量**：过多 (`> 500`) 说明合并压力大，影响查询性能
- **Level 0 Part**：新写入的 Part，数量多说明写入频繁但合并跟不上
- **非活跃 Part**：合并后等待清理的旧 Part，积压说明磁盘空间不足
- **分离 Part**：异常分离的 Part，需要检查原因并决定 ATTACH 或 DROP

## 常见误区

| 误区 | 正确做法 |
|------|---------|
| 频繁执行 `OPTIMIZE TABLE FINAL` | 依赖后台自动合并，仅在 Parts 数 > 500 或查询性能明显下降时手动触发 |
| 所有查询都用 `system.query_log` | 本集群已禁用 `system.query_log`，统一使用 `system.query_thread_log` + `SET log_query_threads=1` |
| 磁盘使用率超过 90% 才告警 | 设置 WARNING 80%、CRITICAL 90%，留足合并和排序的临时空间需求 |
| 备份只存一份本地 | 遵循 3-2-1 原则：3 份备份、2 种介质、1 份异地，使用 BACKUP 命令支持 S3 远端存储 |
| 升级时直接停服升级 | 使用滚动升级，逐节点替换，保持服务可用；先升级从节点，再升级主节点 |
| 忽略 `system.text_log` 中的 Warning | Warning 往往是 Error 的前兆，应每日检查，重点关注 `Raft` 和 `MergeTree` 相关日志 |
| 所有表都用 ReplicatedMergeTree | 非关键数据用 MergeTree 减少 ZK/Keeper 压力；临时表用 Memory 或 Log 引擎 |
| 告警阈值设得越灵敏越好 | 合理设置持续时间和静默期，避免告警风暴；使用 P50/P95/P99 分位数确定合理阈值 |
| Mutation 可以随便执行 | Mutation 是异步且重量级的操作，大范围 UPDATE/DELETE 会阻塞合并，应分批执行 |
| `FREEZE` 备份仍然可用 | 从 CH 22.8+ 开始 `ALTER TABLE FREEZE` 已废弃，统一使用 `BACKUP` 命令 |
| 分区键选择越大越好 | 分区粒度过细导致 Part 数量爆炸，建议分区大小控制在 1-100GB，月分区通常是合理选择 |
| 监控只关注磁盘就够了 | 内存 OOM 和 CPU 过载同样致命，需要同时监控查询延迟、内存使用率和 CPU 负载 |
| 扩容只需加磁盘 | 数据量增长到 TB 级后，计算和存储都需要扩展，单分片不建议超过 10TB |

## 最佳实践

1. **监控优先**：部署新集群后，先配置监控和告警，再上线业务。监控是运维的"眼睛"
2. **自动化运维**：将日常检查脚本化、定时化，Cron 定时执行 `07_routine_maintenance.sql` 中的维护脚本
3. **文档化操作**：所有运维操作记录在案（使用 `maintenance_log` 表），便于复盘和审计
4. **演练常态化**：每月至少一次灾难恢复演练，验证备份的有效性和恢复时间的准确性
5. **基线化管理**：记录性能基线（P50/P95/P99 查询延迟、QPS、磁盘使用率等），对比发现退化
6. **容量预警**：提前 30 天预测磁盘和内存使用，设置 80% 使用率预警、90% 紧急扩容
7. **渐进式变更**：先灰度、再全量，始终有回滚方案；配置变更先改一个节点验证
8. **数据生命周期管理**：明确热/温/冷数据的存储策略和 TTL，热数据 SSD + 冷数据 S3 分层存储
9. **查询治理**：识别慢查询和高内存查询，推动业务优化；限制单用户资源使用
10. **版本兼容性**：升级前查阅 changelog，注意 breaking changes。BACKUP/RESTORE 的版本兼容性需要验证
11. **Keeper 容量规划**：ClickHouse Keeper 的节点数建议为奇数（3 或 5），避免脑裂
12. **告警降噪**：使用告警聚合和升级机制，避免故障期间告警风暴淹没关键信息
