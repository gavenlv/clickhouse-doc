## 核心原理详解

### 1. ORDER BY 决定物理存储顺序

ClickHouse 中 `ORDER BY` 不仅仅是排序，它决定了：

- **物理存储顺序**：数据在磁盘上的排列完全按照 ORDER BY 列的顺序
- **稀疏索引结构**：主键索引基于 ORDER BY 列的每 8192 行生成一个标记
- **压缩率**：有序数据的压缩率远高于无序数据（相同列值连续排列）

```sql
-- 正确：高选择性在前，时间在左
ORDER BY (user_id, event_time)
-- 错误：低选择性在前
ORDER BY (status, event_time)
```

### 2. 稀疏索引依赖主键顺序

CH 的稀疏索引不是 B-Tree，而是**每 8192 行（granule）记录一个主键值**：

- 查询时通过二分查找定位 granule
- 主键列在 WHERE 中必须**从左到右匹配**才能有效利用索引
- 跳过早的列会导致索引失效

### 3. 物化视图预聚合

物化视图本质是 **INSERT 触发器**：

- 数据写入基表时，自动触发 MV 的 INSERT
- MV 存储的是预聚合结果，查询时直接读取
- 适用于：汇总统计、时间窗口聚合、预计算

### 4. 字典编码

字典将键值对加载到内存中，查询时通过 `dictGet()` 函数直接获取：

- 比 JOIN 快 100 倍以上
- 支持 6 种布局，适应不同场景
- 自动刷新策略（LIFETIME）

## 常见误区（10+ 条）

| # | 误区 | 正确做法 |
|---|------|---------|
| 1 | `ORDER BY 随便选，反正有索引` | ORDER BY 必须按查询过滤条件设计 |
| 2 | `用普通 JOIN 查维度字典` | 使用字典替代 JOIN，性能提升 100x |
| 3 | `物化视图可以随便 ALTER` | MV 只能 DROP 后重建，无法在线修改 |
| 4 | `分区越细查询越快` | 分区数过多导致 parts 爆炸，反而变慢 |
| 5 | `宽表永远比星型好` | 列数太多（>200）时星型模式更优 |
| 6 | `主键加得越多越好` | 主键列越多，索引越宽，存储开销越大 |
| 7 | `跳数索引可以替代主键` | 跳数索引是辅助，主键是基础 |
| 8 | `ReplacingMergeTree 能实时去重` | 去重发生在 merge 时，不是查询时 |
| 9 | `物化视图会同步更新基表数据` | MV 是单向的，基表更新不会同步到 MV |
| 10 | `时间字段必须放在 ORDER BY 第一位` | 高基数字段在前，时间在中间 |
| 11 | `字典数据量大了就换 JOIN` | CACHE 布局支持大数据量字典 |
| 12 | `TTL 设置后立即生效` | TTL 在 merge 时执行，有延迟 |

## 最佳实践（10+ 条）

| # | 最佳实践 | 说明 |
|---|---------|------|
| 1 | **查询驱动设计** | 先分析查询模式，再设计 ORDER BY |
| 2 | **高基数在前** | ORDER BY 第一列选高基数字段 |
| 3 | **时间在左但不一定第一** | 时间列放在 ORDER BY 中间位置 |
| 4 | **宽表优先** | 默认使用宽表，200 列以下不拆分 |
| 5 | **字典替代 JOIN** | 维度数据用字典，不要用 JOIN |
| 6 | **物化视图做预聚合** | 使用 MV 做预聚合，查询更快 |
| 7 | **分区不要过细** | 按月分区，数据量大按天 |
| 8 | **TTL 策略必设** | 数据保留策略提前规划 |
| 9 | **LowCardinality 优化** | 低基数字段使用 LowCardinality 类型 |
| 10 | **测试验证** | 生产前用真实数据量测试 |
| 11 | **监控 parts 数量** | 每个分区 parts 数控制在 10 以内 |
| 12 | **避免频繁 ALTER** | CH 的 ALTER 是异步后台操作 |
